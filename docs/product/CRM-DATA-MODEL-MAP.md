# CRM Data Model Map

Generated from a full read of `prisma/schema.prisma` (27 models, 2026-10-02) plus the five subsystem audits behind `docs/product/CRM-CURRENT-STATE-AUDIT.md`. Every model below is scoped to a single `Workspace` (shared-schema multi-tenancy) unless noted. "Usage" reflects what application code actually does, not what the schema permits.

## Legend

| Usage | Meaning |
|---|---|
| **Active — core** | Read/written by multiple features; load-bearing |
| **Active — single-feature** | Read/written, but only by one feature area |
| **Partially used** | Schema fields exist that no code ever reads or writes |
| **Dead** | No application code creates, reads, or updates it (confirmed by repo-wide grep) |

---

## Central models (most features depend on these)

**`Lead`**, **`Opportunity`**, **`AuditLog`**, **`WorkspaceMember`**, and **`Activity`/`Task`** are the five models the rest of the system is built around. `Lead` alone is touched by Lead Management, WhatsApp, Intelligence, Scoring, Property Matching, the Automation Engine, Pipeline conversion, Tasks, Calendar, Notes, and Insights — changing its shape has the widest blast radius in the codebase.

## Findings specific to the data model

1. **`Note` and `Attachment` are dead weight in the schema relative to the product surface.** `Note` is fully wired server-side (validated, audited, workspace-scoped) but has no UI path in or out — not even the "read" direction, since the three detail pages that fetch `noteEntries` never render them. `Attachment` has no code touching it at all.
2. **No composite/unique constraint prevents duplicate `Lead` rows.** `(workspaceId, email)` and `(workspaceId, phone)` are plain indexes, not unique constraints — manual creation and the WhatsApp-inbound path can both create duplicate people for the same contact details; only CSV import has its own in-memory + DB dedup pass.
3. **`PipelineStage` and `Automation` are schema-ready for configuration that the product never exposes.** Both have `Json`/flexible fields (`conditions`, `actions`, `order`, `probability`, `isWon`/`isLost`, `accentColor`) clearly designed for an admin UI that was never built — today both are fixed seed data, editable only by someone with direct database access.
4. **Cross-tenant foreign-key integrity is enforced only in application code** (`assertRelationsInWorkspace`, `src/lib/tenant.ts`), not by the database — there are no composite `(workspaceId, id)` foreign keys. This is already tracked as finding F-21 in `docs/security/DATABASE-SESSION-SECURITY-AUDIT.md`.
5. **`User.phone` and `User.image`** are schema fields that no application code ever sets or reads (already tracked as F-20 in the security audit) — listed here for completeness of the data-model picture.
